# Retire the shared stock key, don't buy another

*Provider names and sources are kept in a private copy.* This version refers to the provider the firmware uses today as **the current provider** and to the others as **Provider B** through **Provider I**, plus a few descriptive labels (a no-key portal endpoint, a crypto-only provider, two kinds of free host). The labels are used the same way throughout.

**No, the club should not get its own key from the current provider now.** Its free plan cannot carry a club: 800 credits a day covers fewer than two devices, and the plan's license says the data may not be shown to users. The cheapest paid plan that fits costs **$288 a year billed annually** (verified live) and would carry 20 devices on quota. But the provider's terms forbid sharing credentials, and they limit display to the account holder's authorized users, a term written for employees and contractors, not club members at home. A club key compiled into the firmware would also be public the day it shipped: plain `strings` on a club release `.bin` prints the current key in clear text (measured). **The recommendation is per-user keys entered on the device's settings page, with no shared key behind them.** That is what issue #65 proposes, with one change: **drop the shared-key fallback.** An empty key should show a "set up your stock key" screen, not borrow someone else's account. A club key makes sense only if the current provider approves the arrangement in writing, and even then it belongs behind a small club-run caching server (a "proxy"), never in the firmware. The current provider's free plan is also the weakest legal fit of the per-user options. Provider B and Provider C license personal use more plainly, so the firmware should be able to use one of them as well. That second provider is a follow-up, not a blocker.

## Recommendation, and how it changes issue #65

In order: **ship #65 without the fallback, write to the current provider with one question, and add a second provider only if the answer is no.** Shipping #65 means a stock-key field on the settings page, stored in the device's NVS (the ESP32's small settings store, separate from the firmware image) next to the weather key it already holds. When the field is empty, the Stocks page shows a sign-up prompt and makes no API calls. The hard-coded key comes out of the club's source, so club releases stop redistributing it. The question for the current provider: does the free plan cover one person showing quotes on their own desk display, and would a key on the cheapest fitting paid plan, serving roughly 20 club members, be allowed? The answer settles both open legal questions below. If either answer is no, add Provider B or Provider C as a selectable provider. The current provider takes free sign-ups with only a name, email and password (no card, no phone), and its own error message says the key is issued instantly.

Three firmware changes help every option, so they belong in #65 or a sibling issue. First, **fetch US equities only during market hours.** With crypto kept on 24 hours, the default list then drops from 480 to about **200 credits a day** on weekdays (arithmetic from the published limits). That leaves room under any free tier. Second, **fetch each distinct symbol once**, even when it appears on two screens; upstream issue #282 records that bug. Third, **treat a 200 response whose body says `"status":"error"` as a failure.** The current provider reports quota errors as JSON with a `code` of 429 ("too many requests"). When that happens, wait for the next minute, or for the 00:00 UTC daily reset (7 pm EST), and keep showing the last good price with an age marker instead of blanking the screen.

## The shared key fails on terms, secrecy and quota at once

The current provider's terms prohibit sharing credentials or allowing unauthorized access, and require customers to keep credentials confidential. Credentials expressly include API keys. A key in public firmware breaks both rules whatever plan it sits on. If it is a free key, two more problems apply: free-tier data may not be used commercially, and the free plan's license line limits it to testing, evaluation and development, with no display to users, no external sharing and no production use. The provider can suspend an account for excessive usage that affects other customers. The project would get no warning before every device went blank.

Secrecy is not achievable. **`strings -n 8` on a club release `firmware.bin` (1.9 MB, built 2026-11-12) printed the provider's full request URL, key included** (measured 2026-11-19). OWASP lists exactly that command as step one of firmware analysis ([OWASP IoT Firmware Analysis](https://wiki.owasp.org/index.php/IoT_Firmware_Analysis)). The key also appears in a log pasted into a public upstream issue (upstream issue #291). A contributor reported that the default build prints it to the serial console (upstream issue #176). The ESP32's flash encryption does not help. It protects the copy inside one chip, but update images stay plaintext until the device writes them, and the release mode permanently burns fuses and can "soft-brick" a board flashed wrongly ([Espressif flash encryption](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/security/flash-encryption.html)). **Any key in a downloadable `.bin` is a public key**, whoever pays for it.

Quota is the third problem. The current provider charges **1 credit per symbol on `/quote`**, and putting several symbols in one call saves network round trips but not credits. One device on today's schedule spends 480 credits a day. The free plan allows 800 a day and 8 a minute, so **one free key covers 1.67 devices**. That limit applies to the current key unless it is on a paid plan. The upstream maintainer described the keys as paid keys that he had hidden as well as he could, while conceding that anyone looking could find them (upstream issue #176). On a paid plan the risk moves from throttling to the owner's bill. The upstream fix was proposed and never adopted. Upstream issue #316, which would route keyed APIs through a maintainer-run proxy, has been open since 2025-03-31 with no decision, and upstream has merged nothing since that date. **The club cannot wait on upstream.**

## A club key costs $288 a year and buys a permission question

On quota alone, a club key works. The current provider's paid plans have **no daily cap, only a per-minute cap**. Twenty devices spend 9,600 credits a day, an average of 6.7 a minute. **The entry paid plan (55 credits a minute; $29/month, or $24/month billed annually) fits**, provided no more than 11 devices refresh in the same minute. Spreading each device's start time across the 15-minute window keeps them under that. The next tier up (144 a minute; $49, or $41 annually) covers 28 devices firing at once. A higher plan ($99/month) adds real-time European data, which the config's promise of non-US exchanges would need. The entry and next paid tiers show other markets at end of day only, and the free plan does not cover them at all. Split 20 ways, the entry paid plan is $14.40 a member a year. That is the strongest argument for a club key: one provider, every display field in one call, and no member ever signs up for anything.

The license is where it breaks down. The entry paid plan's license line permits view-only, internal use within the customer's own applications and dashboards. The terms allow display to the customer's authorized users, defined as the customer's employees, contractors and its own automated systems. Display to anyone else needs a redistribution add-on or a separate agreement. Club members using devices at home are not obviously any of those. The provider has no nonprofit, club or open-source program. The only discount is 20% for students, educators and early-stage startups, none of which describes the club. Redistribution and white-label rights exist only under a separate agreement for business customers. The prices on the commercial-use plans could not be read, because the page draws them with JavaScript. **A club key is a reasonable thing to ask the current provider for, and a bad thing to assume.**

If the current provider does say yes, the key goes on a server the club controls, not in the firmware. Each device sends a per-device token that the member types into the settings page. A leaked token can then be cut off without reflashing anyone, and the provider key never leaves the server's secret store.

## Other providers license personal displays more plainly than the current provider's free plan

Every reviewed provider with a free tier licenses it for personal, non-redistributed use. Several expressly ban sharing access: Provider B limits use strictly to the individual and bans sharing with anyone else; Provider H bans sharing within groups; and Provider I says plainly that sharing is not allowed. **No provider makes a shared club key cheap or clean.** The flip side is that a member's own key on their own desk display fits these terms better than the current provider's free-plan wording does. Provider E's license covers private, individual activity. Provider C's developer guidance says outright that each user must have their own API token. Free tiers also keep shrinking. One well-known free quote API shut down entirely in August 2024. A free CSV quote source now returns 404 and puts a browser proof-of-work check in front of its data (measured). Provider C's single-exchange last-trade price went null in February 2025, pending a signed exchange agreement. Firmware that can talk to more than one provider survives the next such change. Firmware tied to one provider goes blank.

Two findings shape the firmware work. First, **only the current provider and the portal endpoint return every display field in one call.** For Provider B, C or E, the firmware should split fast data (price and change, every 15 minutes) from slow data (name, currency, 52-week range, once a day). Provider B then needs 5 `/quote` calls per refresh plus 10 calls once a day, well under 60 a minute. Second, **the BTC slot needs no key at all.** The crypto-only provider's keyless price endpoint and Provider D's crypto snapshot both answered without a key (measured). The crypto-only provider's free registered tier asks for attribution, so a small credit line on the settings page covers it. The portal's unofficial chart endpoint is the most complete free source. It covers US stocks, London stocks (in pence, "GBp", which the currency logic must handle), forex and crypto. It is also the most fragile. In one session, chart requests that differed only in the portal's hostname and the browser ID string got 429 "Too Many Requests" with a full desktop-browser string or none at all, and 200 with a minimal one (measured). A popular open-source client library for that endpoint has tracked its login-cookie breakages and IP blocks since 2023. **Use the portal endpoint, if at all, as an opt-in experiment, never as the default fallback.** It carries no license to rely on, and every orb on one home network shares one throttle.

## A club proxy cuts provider calls 4–15x but turns a key into a service

A proxy is a small server that fetches each symbol once and hands the result to every device. Provider load then scales with **the number of distinct symbols, not the number of devices**. Twenty devices calling the current provider directly spend 9,600 credits a day. A proxy covering 20 distinct symbols spends 1,920. If everyone shows the default five, it spends 480 (arithmetic). It can also send each device a few hundred bytes of plain text in one request instead of five full JSON replies, which saves ESP32 memory and four TLS handshakes (the encryption setup each HTTPS connection costs). Hosting is free. **A serverless edge host's free tier allows 100,000 requests a day and 5 scheduled jobs per account.** Twenty devices would use under 10% of that. The one trap is that host's key-value store, which allows only 1,000 free writes a day: write one combined record per refresh, not one per symbol. A sleeping free web host is a poor fit. It sleeps after 15 idle minutes and takes about a minute to wake, which is longer than a typical ESP32 request waits. Another serverless host has announced its own shutdown for April 2027. A named hostname needs a domain, about $14/year **[ESTIMATE, +40%]**.

The proxy does not fix the license. Serving one account's data to members is redistribution under the current provider's terms unless the provider agrees. The same contributors who wanted keys out of the firmware warned that a shared proxy would be a large single point of failure and that one bad actor could get everyone rate-limited (upstream issue #176). A reference implementation by an upstream contributor exists, but it lacks what a club would need. It caches per symbol *and* per key, so members with their own keys share nothing. It passes the full provider JSON through. And it lets anyone who finds the URL use the default key. A club proxy needs per-device tokens, a symbol allowlist, a daily cap below the provider quota, a status page and alerts. It also needs provider and hosting accounts under a club address with **at least two people holding access**. Mature open-source device projects mostly skip all of this. Home Assistant's weather integrations and a well-known open-source ESP32 e-paper weather display have each user bring a key. A popular open-source LED-matrix clock firmware holds no third-party keys at all; it displays what a home server pushes to it. **Build a proxy only if the current provider approves a club key, or if many members cannot or will not get a key.** If the club builds one, the device tries the member's own key first and uses the proxy only when that key is empty or failing. A proxy outage then affects only members who rely on it. Making the stock API address a settings field now, as upstream issue #315 proposed, keeps that door open without a later firmware release.

## What was not established

Five things matter to the decision and remain open. **The current provider's intent** is the largest. Its terms and its pricing page use different words (a "free tier" and "authorized users" in one, "users" and "production" in the other), no page addresses hobby devices or open-source firmware, and the terms never say whether the free tier means the free plan. Only the provider can settle whether the free plan covers a personal desk display or whether members can be a club's authorized users. **The plan behind the current shared key, and how often it is throttled**, is unknown. No upstream issue reports quota errors. The **commercial-use plan prices** could not be read. **Provider B's paid prices**, and whether its free `/quote` answers forex, crypto or non-US symbols, were not tested, because no key was used. **The club's real symbol overlap**, which sets the proxy's savings anywhere from 4x to 20x, would take a count of members' configured lists. Also unmeasured: whether failed symbols in a batch still cost credits, the exact message for the current provider's daily cap, and whether signup requires email verification before the key works.

## Conclusion

The question "should the club buy a key?" assumed the problem is money, and it mostly is not. At $288 a year a club key is affordable. What the club lacks is permission, and a place to keep a key secret. Neither comes with the subscription. The per-user key in #65 removes both problems for the price of one sign-up per member, so its fallback should not quietly bring them back. The design that holds up longest is per-user keys, a provider field, a no-key crypto path and market-hours fetching. With those in place, a provider cutting its free tier means a settings change, not a firmware release. The one email to the current provider is the cheapest step in this report and should go first: a yes reopens the club-key option, and a no tells the club which second provider to build.
